# 巡检监测发布与安全状态分层的时序反事实

2026-09-28。此前[回调 CPU 追踪](INSPECTION_TELEMETRY_CPU_ENVELOPE_20260927.md)的 52 个活跃周期中，算法步进墙钟中位约 19 ms、完整状态发布中位约 28 ms；两次最长回调的状态发布分别占 274 ms、343 ms。为检验是否能减少长发布对最终目标指令的挤占，本补项只在**独立诊断算法进程**中保留每五次一次的完整监测发布，状态转变立即发布；每次正常轨迹状态入口均继续发送锁存预算 Bool 与 Hold 预算 JSON。正式 v2 节点、已有 launch 和完整任务结果未改。

![供数、候选、最终 Setpoint 与 PID 原始消息点](../../results/v2/inspection_telemetry_partition_20260928/figures/monitor_partition_timeline.png)

四趟短探针均未过预设严格门。前三趟健康输入最大空档为 0.773、0.314、1.064 s，均大于 0.25 s，不能用来单独估计分频收益；其中第一趟与论文编译重叠，明确保留为并发负载记录。第四趟供数 **46 次、最大空档 0.184 s**，输入门通过；包装脚本[实测计数](../../results/v2/inspection_telemetry_partition_20260928/every5_counted/telemetry_partition_counts.json)显示 63 次正常轨迹状态入口中完整发布 13 次、跳过 50 次，说明分频确已执行。该趟健康最终 Setpoint 为 **27/40** 正向，最大接收空档 **0.318 s**，仍未达到全部正向和 0.30 s 连续性门。故障守卫窗 Setpoint 16/16、PID 3/3 零；恢复段 29/35 Setpoint 正向。图只显示原始消息点，空档未插值。

这一组数据支持的结论是：在至少一趟输入满足已声明门限的本机合成运行中，即使完整监测发布有约八成正常轨迹状态入口被跳过，最终输出仍不连续。它**不能**证明分频完全无效，因为没有同载配对的尾部 CPU／DDS 时间轴；也不能把三趟输入失约的结果算成算法自身失败率。完整监测的 0.5 s 到达上界、操作员状态变化延迟与完整航程均未单独验收，因此分频包装脚本只保留在 `tools/` 作隔离诊断，不进入产品配置或 PPT 主讲。

[四趟逐消息日志、脚本快照与哈希](../../results/v2/inspection_telemetry_partition_20260928/README.md)提供复核入口。下一步应先固定目标计算平台的 CPU、ROS/DDS 与传感器采集并发负载，在同次有限路线内测量决策、状态发布、最终授权、PID、桥和板端回执的尾部时差；任何降低完整监测频率的设计，须额外验证预算告警逐周期发布和操作员状态突变及时显示。当前 `field_release_authorized=false`。
